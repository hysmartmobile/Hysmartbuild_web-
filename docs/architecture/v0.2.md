# V0.2 — Identity, Companies, Tenant Isolation and RBAC

## Decisions
- Registration creates a Supabase Auth user. Passwords are never copied into application tables.
- The onboarding flow is: register → verify/sign in → create company → receive COMPANY_OWNER membership.
- Tenant identity is derived from the authenticated Supabase user and membership records. API clients cannot select a tenant by supplying an arbitrary company ID to create data.
- Express uses the Supabase service-role client only on the server. The browser/mobile clients use the Supabase anon key for authentication.
- Rate limiting is an in-memory implementation behind a small class interface so Redis can replace it later without changing route contracts.
- Supabase RLS is enabled as a second tenant-isolation boundary. Server-side authorization remains mandatory because service-role access bypasses RLS.

## API
- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `GET /api/v1/me` (authenticated)
- `GET /api/v1/companies` (authenticated; only memberships of current user)
- `POST /api/v1/companies` (authenticated; creates company and current user's COMPANY_OWNER membership)
- `GET /api/v1/companies/:companyId/membership` (authenticated; only returns a membership belonging to current user)

## Tenant boundary
All future tenant-scoped services must accept the authenticated user ID and resolve/verify membership server-side. A request body `companyId` must never be treated as proof of access.
