# V0.3 RBAC & Authorization

V0.3 turns the V0.2 RBAC schema into an enforced authorization boundary.

## Request flow
1. Supabase access token is verified by `authMiddleware`.
2. `authorize(permission)` resolves `companyId` from the route parameter.
3. `RbacService` queries the authenticated user's active membership for that company.
4. The member's role is resolved to permission keys through `role_permissions`.
5. The request proceeds only when the required permission is present.
6. Supabase RLS remains an independent database boundary.

## Design rules
- Tenant identity comes from authenticated membership, not request body ownership claims.
- Roles are canonical values in the database and code.
- `SUPER_ADMIN` is not assignable through normal company administration.
- A company cannot lose its final active owner.
- Self-role changes are blocked.
- Authorization logic is centralized in `authorize.js` and `RbacService`.
- Redis can later replace rate-limit storage without changing authorization contracts.
